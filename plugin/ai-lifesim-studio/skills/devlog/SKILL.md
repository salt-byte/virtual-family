## 每节格式

```markdown
## <编号>. <一句话标题>
问题（用户反馈 / 自测发现）：<原话或现象；没有就省略这行>

做法：
1. <做了什么、改了哪个文件、为什么这样做>
2. …

问题和修正：
- <现象> → <原因> → <改法>

决定：
- <问题> → <决定> → <放弃的方案和为什么> → <后果 / 代价>

证据：<verify run_id、--playtest 打印的关键行、留存截图路径 production/qa/evidence/…<!-- TODO(lifesim): 原文指向 playtest-automation，本插件暂无对应技能 -->>
```

「决定」和「证据」两段是新加的：
- **决定**：凡是两种做法都说得通、最后选了一种的，都要留一行。看得见放弃了什么，之后才有人敢改。改一个系统前列的变更影响清单也放在这里，改完逐条勾<!-- TODO(lifesim): 原文指向 producer，本插件暂无对应技能 -->。
- **证据**：不写「测试通过」，写证据在哪：`qa/verification.json` 的 run_id、`[playtest]` 打印的那几行、截图的路径。看完就删的截图不算证据。

## 写法
- 写给没参与的人看：每个决定写原因（「旧地图不动，因为剧情坐标和存档都依赖它」）。
- 写清**踩过的坑和教训**，这是最有价值的部分（例：「编辑器里一直正常，只有导出版漏了 .yarn → 以后每次都在网页版上再测」；「留了个解析错误，游戏卡在空窗口永不退出，等了 6 分钟才发现 → verify.py 先过解析门」）。
- 数字要具体：48×36 → 96×72、224 条文字、6 → 13 件家具。
- 有对照、清单时用表格（候选素材淘汰表、新房间表、小人动作表）。
- 不写成就感式总结，不写「顺利完成」。
